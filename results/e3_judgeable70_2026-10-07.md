- **New fault: effective context is 16K, not 32K.** The sample sampling config requests max_output_tokens = 16,384 on every call, so vLLM
  rejects any request whose prompt exceeds 16,384 tokens (`ContextWindowExceededError: ... requested 16384 output tokens and your prompt
  contains at least 16385 input tokens`). 15/70 runs (21%, CI 13-32%) crashed this way, after a median of 16 turns (7-49).
  The crash discards the run: all 15 have an empty agent_patch. Completions never need that reserve: median 84 tokens, p99 2,709, max 8,578;
  1 of 2,177 completions exceeded 6,144 tokens. The harness does compact history (63 runs, 136 compactions, median pre-compaction prompt
  14.6K), but one turn's completion plus tool result can jump past 16,384 before compaction runs (e.g. 12,184 + 4,681-token completion).
  Config-only fix: lower max_output_tokens (e.g. 8,192) so input can reach ~24K.
- Labeler v0.2 gap: it reported compactions=0 in every run and labeled all 15 crashes BUDGET (the crash text is in result.error_message, which
  the adapter did not read). Adjudicated by hand as CONTEXT.
- Process: 2,177 turns; schema-invalid 96 (4.4%, CI 3.6-5.4%: 33 repaired, 61 rejected, 2 no-call); edit_file failed 77/209 (37%:
  19 runtime [12 EDIT_NO_MATCH, 6 EDIT_FAILED, 1 budget], 58 rejected). All 58 rejected edits lack old_string (corrupted argument key: code
  containing a double quote parsed as a key, e.g. keys [filepath, new_string, else]); they come from 5 runs (18, 14, 12, 9, 5), 4 of which still
  resolved. So the corrupted-key defect persists without the RQ4 'never escape' rule (5/70 runs vs 1/16 in the pilot): the RQ4 reading
  that the rule caused it is not supported.
- Over-escaping returned without the escape rule: 64 edit_file calls carried >=2 literal \n and no real newline (14 runs); 35 failed.
